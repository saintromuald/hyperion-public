# The pinned ShieldBattery platform

ShieldBattery's platform (accounts, matchmaking, MMR, ladder points, leagues,
seasons), vendored under `engine/tools/shieldbattery/` as the ladder port's
server (`docs/sb-platform-port.md`). The pre-release runs it beside the
engine, and the engine speaks its HTTP/WebSocket APIs directly; the parts of
ShieldBattery that only exist to launch and hook StarCraft: Remastered are
trimmed out.

- Upstream: https://github.com/ShieldBattery/ShieldBattery
- Fork: none yet — create `saintromuald/ShieldBattery` before the first rebase
- Pinned commit: `abdeb8ae23b841e36535b01890c5302347948c06` (upstream master,
  2026-10-31)

## The trim

| Dropped | Why |
|---|---|
| `app/` | the Electron launcher that starts SCR and injects the game DLL; Hyperion's engine is the client (plan Decision 2) |
| `game/` | the Rust DLL that hooks SCR's netcode and reports results; Hyperion reports its own results |
| `integration/` | Playwright tests that drive the Electron app |
| `deployment/` | ShieldBattery's production Kubernetes manifests — except `deployment/appserver/db/`, which `docker-compose.yml` mounts for local Postgres setup |
| `server/public/` | the built web client (13 MB); regenerated by the client build (`pnpm build-client`-style scripts, see `package.json`) |

## The Hyperion-specific delta

Changes made to the vendored tree, tracked here so a rebase can re-apply them:

- `.gitignore`: `target/` (Rust build output for `server-rs`; upstream's list
  has no Rust ignores because upstream builds Rust outside this tree).
- `common/games/configuration.ts`: `GameEngine` (`'scr' | 'hyperion'`) and an
  optional `engine` field on game configs (absent = `scr`).
- `server/lib/network/electron-clients.ts`: `isHyperionClient` — an
  `Origin: hyperion://…` connection is a Hyperion engine client.
- `server/websockets.ts`, `server/lib/websockets/session-lookup.ts`,
  `server/lib/websockets/socket-groups.ts`: a third `clientType`, `'hyperion'`.
- `server/lib/matchmaking/matchmaking-api.ts`: `/find` no longer requires
  `clientPubkey` (Hyperion clients have no netcode v2 session to mint).
- `server/lib/matchmaking/matchmaking-service.ts`: the queue carries each
  player's engine (derived from client socket type); Electron clients without
  a pubkey are refused in the service; mixed-engine matches are refused; the
  stored game config carries `engine` for Hyperion games.
- `server/lib/games/game-loader.ts`: Hyperion games never create a netcode v2
  session; their `localOnly` load completes on the players' own
  `PUT /:gameId/status` Playing reports (fault for a missing report falls on
  that player, like a lone-human game's).
- `server/lib/games/game-api.ts`: `POST /api/1/games/:gameId/results` — the
  resultCode-authed result submission the Hyperion engine uses instead of a
  relay webhook; the report validates against
  `SUBMIT_GAME_RESULTS_REQUEST_SCHEMA` (legacy or raw shape).
- `tools/hyperion-gate/`: the Phase 1 gate. `gate.sh` boots Postgres/Redis
  (compose), applies the migrations (a mini sqlx-compatible runner), starts
  server-rs and the Node server, seeds the dev accounts, and runs `gate.mjs`
  — a scripted two-client Hyperion match (login → queue → accept →
  setGameConfig → started → results → reconciled rating changes) driven over
  plain HTTP + WebSocket with `Origin: hyperion://…`.

## Rebasing

Copy a fresh clone at the new rev with the same trim:

    rsync -a --exclude .git --exclude /app --exclude /game --exclude /integration \
        --exclude /deployment --exclude /server/public \
        <fresh-clone>/ engine/tools/shieldbattery/
    # plus the one deployment subtree docker-compose.yml mounts:
    rsync -a <fresh-clone>/deployment/appserver/db/ engine/tools/shieldbattery/deployment/appserver/db/

then re-apply the delta list above, diff against the previous pinned rev to
catch unintended drops, and run the Phase 1 gate (the scripted two-client
match) before committing.
